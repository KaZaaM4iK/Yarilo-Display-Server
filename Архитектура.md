Дополнительные компоненты — отдельно:
- Внешний Window Manager (WM) — задаёт оконную политику, а не композитор.
- X11-совместимый мост — отдельный компонент для старых X11-приложений.
- Wayland-совместимый мост — отдельный компонент для совместимости с существующими Wayland-приложениями.
Это принципиально: не нужно встраивать оконную политику внутрь графического сервера только потому, что так проще сделать первый прототип.
2. Ключевые договорённости, которые нельзя потерять
Компонент	Принятое решение
Ядро и композитор	Один процесс в первой версии, логически разделённые подсистемы
Оконная политика	Только внешний WM; сервер реализует строгие механизмы
Surface / Buffer / Commit	Раздельные сущности с разными жизненными циклами
Первоначальная отрисовка	Полная перерисовка кадра — Full Redraw, без incremental damage tracking
Буферы	Нельзя переиспользовать, пока не завершено чтение всеми потребителями
Синхронизация	Явные зависимости acquire/release; никаких предположений, что GPU уже закончил работу
DRM/KMS	Один незавершённый page flip на выход
Обратная связь	BufferReleased и FramePresented — разные события
Ошибки и отключения	Нельзя освобождать ресурсы, пока DRM или потребители ещё могут ими пользоваться
Платформы	Linux и FreeBSD; платформенные различия изолируются в backend
Графические API	GBM — деталь backend, а не обязательная часть архитектуры всего сервера

3. Самая важная часть — жизненный цикл кадра
Мы отдельно прорабатывали этот механизм, потому что именно здесь легко получить повреждение изображения, use-after-free и гонки синхронизации.

flowchart TD
    A["Клиент передаёт Commit"] --> B["Проверка Surface, Buffer и последовательности"]
    B --> C["Проверка зависимостей и Reader Leases"]
    C --> D["Compositor читает SHM и композитит в Back"]
    D --> E["Чтение клиентского буфера завершено"]
    E --> F["BufferReleased"]
    F --> G["Page flip в DRM/KMS"]
    G --> H["DRM_EVENT_FLIP_COMPLETE"]
    H --> I["FramePresented"]
    I --> J["Буфер вывода можно использовать в следующем кадре"]

Здесь два события имеют совершенно разные гарантии:
- BufferReleased — сервер закончил читать клиентский буфер. Клиент может повторно использовать его, если не осталось других активных читателей.
- FramePresented — завершился соответствующий page flip. Это подтверждение показа кадра, а не просто завершения копирования пикселей.
В текущем CPU-прототипе чтение SHM завершается синхронно внутри blit_subsurface(), поэтому отправка BufferReleased после успешного blit допустима. При появлении асинхронных GPU-потребителей этот контракт придётся обеспечивать через явную синхронизацию.
